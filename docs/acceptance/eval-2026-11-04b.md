# Verdict: not yet

4 November 2026. Re-evaluation against `demo-bar.md`, using the previous evaluation's severities: blocker = stops a task, shows something false or breaks the page; major = completes but invites a first-time visitor to get stuck or misread; minor = craft. **One blocker, four majors and one minor** are recorded below. No application code was changed.

The original E1–E10 fixes substantially improve the demo. Saving a scenario now exposes a different baseline-label error, and the new reference/marker integration still needs work. Custom level, absent starting-point editors and human-readable values **inside the scenario chip** are deliberately excluded because another branch is implementing them. Findings about already implemented rule choices and marker tooltips concern their present behaviour, not missing features.

## Findings

### B1 — blocker — Saving separated lists changes the number labelled “officially”

**Combinations:** all eight, directly exercised.

**Steps:** 2022 → Standard → United Torah Judaism → What if they had run separately? → Run as 2 separate lists → close details. Observe the shared baseline explanation. Name and save the scenario in Scenarios → return to Overview.

**Observed:** before saving, the shared comparison correctly reads “Ran separately: together 4, officially 7 as United Torah Judaism”. After saving it reads **“Ran separately: together 4, officially 4 as Agudat Yisrael + Degel HaTorah”**. Hebrew similarly labels the saved four as “בפועל”. The real joint list won seven; saving cannot change that fact. The engine result is not alleged to be wrong. The explanation falsely identifies a saved hypothetical baseline as the real result.

**Expected:** either hide the now-clean comparison or name the saved reference and distinguish it from the real seven-seat result. The same baseline qualification must reach accessible row descriptions: source inspection also finds “more/fewer than the official result” hardcoded while the underlying delta can use the saved reference.

**Evidence:** `.backup-scratch/eval-b/shots/en-light-desktop-T3.png` before saving; `en-dark-phone-saved-reference.png` and `he-dark-phone-saved-reference.png` afterwards. These and the other screenshots below are relative to `.backup-scratch/eval-b/shots/`; the same suffixes exist for all eight prefixes. **Likely file/inference:** `src/app/components/ListBars.tsx`, reference substitution followed by hardcoded `officially` and accessible delta text. This extends E3: duplicate parent baselines are fixed, but saved references are mislabelled.

### B2 — major — A saved custom grouping is denied its own comparison baseline

**Combinations:** all eight.

**Steps:** 2022 → Standard → edit blocs, move New Hope into Coalition, rename the bloc → save as Review A → raise Likud to 1,300,000 votes → Compare against Review A.

**Observed:** the page names Review A as its baseline, and its left chamber contains that reference's **66/54** bloc totals. The right chamber contains **68/52**. Nevertheless the heading says **“custom grouping has no baseline counterpart”**, and the Blocs section draws only the current 68/52 bar, with no baseline bar or paired deltas. Both chambers plainly contain the same saved grouping. The session summary likewise omits bloc deltas against it.

**Expected:** a saved custom grouping is a valid reference for subsequent vote edits that retain that grouping. Draw and label its before/after bloc comparison. Reserve the no-counterpart explanation for genuinely incompatible groupings.

**Evidence:** `en-light-desktop-saved-compare.png`, `he-dark-phone-saved-compare.png`; corresponding all-eight captures. **Likely file/inference:** `src/app/derive.ts`, `groupingBaseline` immediately rejects a null `blocSchemeId`; callers in `Compare.tsx` and `ChangeSummary.tsx`. The original E1's party-seat omission does not recur; this is a reference boundary defect.

### B3 — major — Edit-marker explanations expose internal IDs and JSON, with RTL overflow

**Combinations:** raw marker values reproduced in all eight; overflow visually confirmed in Hebrew dark phone.

**Steps:** 2022 → Expert → Merge & split → Surplus agreements → Start from… → Blank → focus an edited glyph beside the agreement heading. Also inspect the marker after moving a constituent party between blocs.

**Observed:** the agreement tooltip reads, for example, `Agreements · 25-agr-1 · Edited: was {"id":"25-agr-1","members":["25-שס","25-ג"],"enabled":true}`. Membership markers likewise expose stored bloc values instead of the old bloc's name. In Hebrew the JSON and English property names remain, and the agreement tooltip extends left outside the phone viewport; the full-page image expands beyond 390 px to capture it. Five isolated agreement glyphs sit above “None.” without readable partner identities.

**Expected:** explain the previous agreement using the two list names and its enabled state, or the previous membership using the bloc name, in the active language. Keep the tooltip within the viewport and attach the explanation to its meaningful context.

**Evidence:** `en-light-desktop-marker-json.png`, `he-dark-phone-marker-json.png`; `focused.json` records the tooltip labels for all eight. **Likely file/inference:** `src/app/components/EditMarker.tsx` serialises object values; `src/app/derive.ts` falls back to path keys in `editPathLabel`; tooltip CSS in `src/app/styles.css`. This is **outside** the chip and is not the deferred chip-value work.

### B4 — major — Implemented rule starting points are labelled with internal identifiers

**Combinations:** all eight option-list inspections, including Hebrew.

**Steps:** Expert → Rules → open Start from… and inspect the era presets.

**Observed:** choices are `il-1949-highest-average-0`, `il-1951-largest-remainder-1`, `il-1977-bader-ofer-1-candidate-cap`, etc. Hebrew exposes the same identifiers. A newcomer must decode a storage key to choose a historical rule set; the meaningful date, method, threshold and special qualification are not presented as labels.

**Expected:** readable, bilingual era names, with the distinguishing threshold/method or candidate cap where needed. The raw key remains internal.

**Evidence:** `en-light-desktop-rules-start.png`, `he-light-desktop-rules-start.png` locate the control; `focused.json` records every actual option label in each combination. The screenshots show the closed native selector, so the option-label proof is the recorded DOM observation, not a claim that all options are visible in the PNG. **Likely file:** `src/app/components/StartFrom.tsx`, rules options render `r.id`. This reports an implemented editor's labels, not a missing starting-point part.

### B5 — major — Scenario description edits bypass marking and undo history

**Combinations:** all eight.

**Steps:** make a coalition selection → Scenarios → enter “Review description” in Description → inspect Undo and history → activate Undo.

**Observed:** typing the description adds no matching history action or edited marker. Undo still names the previous coalition action (in two Hebrew phone probes the preceding agreement action). Activating it removes the new description **and reverses that unrelated earlier edit**. There is no independent undo step for the description. The description field's direct state update is outside the action log.

**Expected:** the description edit has its own reversible commit and truthful action name, with an edit indication where appropriate. Undoing prose must not also alter coalition or agreement inputs.

**Evidence:** `en-light-desktop-description-before.png` and `en-light-desktop-description-after-undo.png`; all-eight equivalents and `descriptionUndoLabel` / `descriptionAfterUndo` in `focused.json`. **Likely file/inference:** `src/app/components/Scenarios.tsx`, description `onChange` calls `edit` / `setState` instead of an undoable action. This is existing metadata behaviour tested under the owner's “every edit” rule, not deferred Custom work.

### B6 — minor — Saved scenario identity is repeated in the same result view

**Combinations:** all eight saved-reference screenshots.

**Steps:** save as Review A → Overview.

**Observed:** the band chip says “Review A”; immediately below the navigation the summary repeats a standalone “Review A”, followed by **“Since Review A”**. This is three nearby uses of the same identity, even when there are no new seat changes. On phones the repeated text contributes to a multi-line status region before the chamber.

**Expected:** keep the single identity chip and the meaningful reference label; remove the extra standalone scenario name. This does not ask to remove baseline labels where they are needed.

**Evidence:** `en-dark-phone-saved-reference.png`, `he-light-desktop-saved-reference.png`; all-eight equivalents. **Likely file:** `src/app/components/ChangeSummary.tsx`, `.scn-name`, alongside the chip in `TopBar.tsx`.

### Craft, performance and proof limits

No page exceptions, console errors or HTTP error responses were recorded in the main eight-context sequence. There were **21–32 failed-request events per context**, all OSM tile cancellations (`net::ERR_ABORTED`) during map/election navigation. They do not prove a broken map, but the literal no-failed-requests box is not satisfied. Main-task screenshots had document scrollWidth equal to clientWidth throughout. The focused marker-tooltip state exposes the additional RTL overflow in B3, so the global no-clipping box fails.

Screenshots were visually inspected across English/Hebrew, both themes and desktop/phone, particularly saved-reference comparisons, phone threshold editing, agreement tooltips, rules and the Hebrew dark PM-only panel. This was targeted inspection, not a pixel-by-pixel reading of every capture. The matrix records `html` direction as LTR/RTL appropriately. Raw rule IDs and marker JSON prevent claiming complete Hebrew despite the main flows being translated.

Fresh-context, cache-disabled phone timings used Chromium CDP with **4 Mbps download, 1 Mbps upload, 150 ms latency**, no CPU throttle, measuring navigation to the first visible list row. English light/dark measured **1,120 / 943 ms**; Hebrew light/dark **898 / 905 ms**. Results are recorded in `cold.json`; this is local static serving under emulated networking, not a real low-end device or hosted-site guarantee. No edit visibly froze the tested flows. Warm timings in `extra.json` are not used as cold-load evidence.

Keyboard evidence includes Enter on comparison/safety actions, Escape in details and the existing focused regressions. It does not establish every-control keyboard completeness. No screen reader, high-contrast mode, 200% zoom or full contrast-ratio audit was performed; no WCAG conformance claim is made. Every logo, member link, grouping and context source was not independently re-audited. The unit suite reproduces its historical fixtures; that is not proof of every provenance claim.
