# Compare as a two-sided election workbench

Research handoff, 7 November 2026. Repository inspected at `754c93b`. Research only; this document does not implement or approve a UI design.

**Recommendation:** give both sides their own scenario, editing history and named starting point. Put a shared, aligned comparison table beneath a compact results overview. Offer copying at three distinct scales: a field, selected rows, and a whole list or scenario part. Treat historical matching as evidence about relationships, not permission to transplant data automatically.

Confidence is high in these interaction principles as a design starting point, but they have not been usability-tested in this app. No inspected product establishes a complete precedent for two editable Israeli elections with safe cross-era copying. The synthesis below is a recommendation, not a claim that another tool already solves this problem.

## Question, scope and evidence rules

The decision is what a subsequent designer should preserve, adapt or reject when replacing Compare. “Both sides editable” means two independent drafts, including drafts based on different elections. “Copy” means copying an input into the destination and recalculating there; it does not mean moving real voters or copying an allocation result. “Replace a party” needs an explicit distinction between an electoral list and one of its constituent parties.

Four research streams: compare/merge tools; scenario and typed-paste tools; election/results tools; failure cases around matching, denominators, provenance and reversibility. Primary product documentation and public product interfaces qualify. Search snippets only aid discovery. No English Wikipedia was opened or used as evidence. Product documentation establishes advertised behavior, not usability or adoption. Suggestions below are labelled by their position in the recommendation sections rather than presented as observed features.

**Access labels:** **Operated** means a named control was exercised and a state change inspected. **Read-only** means documentation or the public interface was inspected without testing its core workflow. **Limited** means a blocked, missing or restricted page cannot support a feature claim. Operating a documentation disclosure does not count as operating the product.

Method deviation: initial managed-browser visits used that browser's default User-Agent; its controls exposed no User-Agent setting. After repeated “Too many server browser tabs are open” errors, research switched to a separate Playwright context configured with `israel-elections-explorer/0.1 (+https://github.com/YiftahCooper/israel-elections)`. Later source visits and the YAPms/Electoral Calculus operations used that context. Thus the initial visits cannot be claimed to meet the brief's User-Agent condition. No challenge, login or membership gate was bypassed. No observed 429 was retried.

## What the repository already provides

These are source-reading findings, not a browser audit of the app:

- [Compare.tsx](../../src/app/components/Compare.tsx) has one active scenario and a `compareWith` choice. Same-election options include official, reference and saved scenarios; another election loads its official baseline. It already offers paired chambers, bloc summaries, key numbers, seat/vote differences and candidate changes. Its same-election grouping follows origins; its cross-election view deliberately avoids asserting list-to-list equivalence. An unchanged comparison can resolve automatically to a previous election.
- [store.ts](../../src/app/store.ts) defines a `ScenarioSession` with scenario, reference, past and future, but Compare does not instantiate a pair of these sessions. `dispatchMany` already provides all-or-nothing grouped edits to the current scenario. Per-election sessions and scenario drafts preserve work when switching; saved scenarios replay logs. These are useful foundations, not proof that adding a second editor is a selector-only change.
- [Scenario/reference design](../design/scenario-reference-and-custom-level.md) distinguishes result inputs (A), analytical groupings (B), and appearance (C). Saving/loading updates the marker reference. Whole-part replacement has one local marker; subsequent edits use that replacement checkpoint. Numerical comparisons and edit-marker references are independent. Preserve this distinction: the opposite Compare side must not silently become an editor's marker reference.
- [actions.ts](../../src/model/actions.ts) validates integer votes, handles withdrawals, merges/splits, candidate rosters, agreements and rules. `setVotes` is a raw assignment, while other actions express transfers or adding voters. Choosing one action by convenience would silently choose a budget policy. `startPart` and the part registry are existing concepts; arbitrary cross-election entity replacement and rich copy provenance are not established merely by their existence.
- [Decision 0017](../decisions/0017-list-lineage-comparisons.md) records `originIds` for within-scenario structural comparisons. Connected origin groups do not attribute merged votes uniquely to each component.
- [party-lineage.json](../../data/meta/party-lineage.json) is explicitly a draft revision. [registry.ts](../../src/families/registry.ts) exposes merger, split, rename and electoral-partner suggestions and excludes pending/leader-move relationships from succession suggestions. [families/model.ts](../../src/families/model.ts) preserves mixed/unresolved and not-counted states. None of this supplies an observed division of a joint list's votes among constituent parties.

**Implication:** reuse the domain transitions, reference semantics and sourced identities. A second editor, a mapping layer and copy transactions need explicit design. Do not turn `comparisonGroups` or a family membership into a universal cross-election identity matcher.

## Eighteen design principles

1. **Two peers, two drafts.** Each selector can load official history or a saved scenario from any supported election. Editing an official selection creates a draft automatically; it never alters the retained official dataset. Editing either side must not require swapping it into the application's one active editor. [C07, C09; repository store]
2. **Name both endpoints.** A copy action identifies source scenario/election, target scenario/election, entity and field. “Copy votes to B” can be concise, with full names in the accessible label and preview. Physical arrows supplement meaning. [C01, C02]
3. **Keep three comparisons distinct.** A-versus-B answers the user's question; draft-versus-official determines factual result identity; draft-versus-marker-reference shows local edits. A copy origin is a fourth provenance fact, not a replacement for those references. [Repository reference design; C04, C07]
4. **Inputs copy; results recalculate.** Votes, rosters and rules can be inputs. Seats, threshold-vote counts and elected members are derived. A seat-target experiment belongs to an explicit inverse/what-if tool, not a “copy seats” arrow. [C05; repository actions]
5. **Make the copy unit explicit.** Field, selected lists, whole list, scenario part and whole draft are different scopes. State each in the action, with a review for larger scopes. [C02, C06; repository part design]
6. **Alignment is a decision, not an accidental sort.** Use scoped IDs and sourced relationships. Keep unmatched rows visible. Search by historical aliases, but never equate entities just because names, letters or leaders look alike. [C03; repository lineage]
7. **Relationship is not equivalence.** Rename, merger, split and electoral partnership require distinct treatment. A source group can be useful for comparison without being a safe replacement for one target row. [C08, C18; repository lineage]
8. **Ask about consequential ambiguity where it arises.** For a vote copy, clarify raw count versus share and the destination vote-budget policy. Apply the existing Just this once / For this item / Always convention; the preview still states the active choice. Unambiguous same-election field copies need no ceremonial dialog. [C06, C14; owner principles]
9. **Preview consequences as well as changed cells.** Show direct inputs, budget adjustments and recalculated effects on other lists. Do not claim a complete causal decomposition when several inputs changed. [C01, C05, C13]
10. **One intention, one undo.** A bulk copy or replacement either validates and commits in full or leaves the target untouched. The source stays unchanged. Undo restores mapping-dependent references and provenance as well as figures. [C04, C07; repository `dispatchMany`]
11. **A copy is a snapshot by default.** Later source edits must not silently update a destination. A link is a separate, visible dependency with an unlink action; postpone it until dependency semantics are complete. [C06 input/formula distinction; recommendation]
12. **Show origin without marker clutter.** A whole-part copy gets its existing part-level marker. Inspectable details say which snapshot, fields, mapping and policy supplied it. Appearance-only copying remains appearance, not a factual result edit. [C04; repository A/B/C design]
13. **Use counts, rates and rules together.** Display vote counts, share of valid votes, turnout denominator, threshold and rule era. Percentage-point change is distinct from percent growth; unknown and not-contested are distinct from zero. [C10, C15, C19]
14. **Keep overview and exact inspection connected.** Chambers and aggregate numbers orient; aligned rows explain. Selecting a changed aggregate filters or opens its relevant rows, preserving context. [C12, C17; owner product principles]
15. **Do not move the target under the pointer.** Stable alignment/order during editing, matched row heights, retained scroll and independent detail-panel scrolling. Sorting by recalculated seats is explicit. A difference that becomes equal must not vanish mid-click. [C02, C04; owner no-jumps rule]
16. **Alternative inputs do not predict voters.** A transplanted count or hypothetical constituent split is arithmetic, not measured vote movement, intention or an observed historical split. [C14, C18, C19; repository families]
17. **Symmetric meaning survives small screens and RTL.** Use stable A/B identities with names; text mirrors, charts/numbers remain LTR. On phones use paired row values and an explicit target sheet rather than unreadably narrow editors. Copy has button/keyboard/touch routes; drag is an optional shortcut. [C02, C09, C11; owner language rules]
18. **Expose depth without requiring expertise.** Start with result/seat differences and direct vote edits. Disclose mappings, parts, rosters and rules at point of use. Source qualifications, edited state and experimental rules remain visible at every level. [C14; repository level design]

## Concrete capabilities for a great version

These are proposed capabilities, not verified existing features or an implementation commitment.

### Opening and overview

- Two equivalent selectors: election, official/saved/draft identity, status and a small result preview. Both support different elections and different saved scenarios from the same election. Opening the same saved scenario twice produces independent drafts, with clearly named save destinations.
- Each side has its own lock, edit action, dirty state, save-as and reset-to-starting-point. Official data remains available even after both sides become scenarios. Switching either selector preserves unsaved work or offers a clear recovery path consistent with existing drafts.
- “Swap sides” swaps presentation and changes delta direction; it does not copy or modify data. The label fixes the equation, for example “B − A”. Swapping also moves each draft's own history, reference, selection and lock.
- Paired chamber, majority context and exact summaries: seats, valid/cast/invalid votes, turnout, unrepresented votes, threshold, agreements and rule differences. Unequal experimental chamber sizes require both seat counts and seat shares. Threshold proximity matters even where seats have not yet changed.
- Shared table with group labels, A values, B values, signed deltas and copy commands. Views: All / Different / Edited / Unmatched; search and sort are separate. “No seat change” must not hide changed votes, identities, rosters, agreements or rules. Both zero-seat and unmatched lists remain discoverable.

### Editing and copying

| Scope | Concrete action | Required semantics |
|---|---|---|
| One number | Copy this vote count to the paired row | Exact integer count; target budget policy; source snapshot; recalculate target. |
| Share | Use this list's share in the target | Define target valid-total policy, exclude/include target in the calculation, deterministic integer rounding and a visible resulting count. Never copy the rounded display percentage. |
| Selected rows | Select several rows, choose Copy votes to A/B | Visible selection count, all-selected versus visible-filter scope, one reviewed transaction, no partial success. |
| Whole list | Replace B's list with A's historical list | Explicit source/target entities and field bundle; IDs remapped; dependencies reconciled; destination rules stay unless separately selected. |
| Part | Start votes / candidates / agreements / blocs / rules from the other side | Same part vocabulary as existing editors, destination-appropriate mapping and validation, one replacement marker. |
| Appearance | Copy colour or display styling | Appearance only under class C; do not generate a factual-result identity. Historical source identity remains inspectable. |
| Entire draft | Duplicate A into an independent comparison draft | New draft identity; explicit election context. This is different from replacing B's inputs while retaining B's election. |
| Drag | Drag a field or list onto a destination | Highlight destination and say “Copy votes” or “Replace list”; incompatible targets explain why. Same action available without dragging. |

- Local commands in a shared gutter should be the default for one-to-one field copies. A selected-row toolbar handles repetition. An explicit “Copy…” sheet handles paste-special bundles and unmatched targets. Avoid showing every possible direction/scope as permanent row buttons.
- Copy choices can cover identity, votes, roster, constituent structure and appearance. Dependencies such as agreements, coalition membership and bloc membership are reconciled explicitly rather than silently inherited. “Whole list” includes a precise field inventory; it is not an unrestricted object overwrite.
- After applying, retain a compact feedback line such as “Votes copied from A · Undo”; inspectable provenance gives source snapshot/revision, source and target entity IDs, fields, mapping, raw-count/share method and budget/rounding policy. Recopying is allowed and replaces the current input; it does not repeatedly add it.
- Locking a field prevents edits or overwrites. Linking a field means ongoing synchronization. These must not share a control. A future link must define direction, cycle prevention, source deletion, unavailable source, recalculation order, save/share portability and unlink-as-snapshot. Until then, offer snapshot copy and lock only.

### Matching and replacement

Three separate operations are essential:

1. **Compare as a group:** align several lists on one side with several on the other; compare aggregate measured inputs/results. This changes analysis, not either election's results.
2. **Map for copying:** select the destination of a particular source input. A user-created mapping is an analytical choice, visibly distinguished from a sourced historical relationship.
3. **Change list structure:** merge, split, add or replace lists in a draft. This changes result inputs and must use domain transitions and their validation.

The matching UI should expose Same identity / Sourced rename / Merger or split / Electoral partners / User mapping / Unmatched, with source details behind (i). Suggest from the existing registry and lineage evidence; never promote every edge to equivalence. Names are search aids, letters are scoped to an election, and family membership is a grouping definition.

A mapping review shows both historical names, dates, source relations and constituent membership. It permits one-to-one and explicit many-to-many groups. Unmatched sources can be ignored for that operation, mapped, or added as synthetic lists; an unmatched destination can remain. “Ignore” must not silently become zero. Display grouping and copy mapping must remain separable, so changing the analytical view cannot retarget a queued copy.

**Owner example: Likud 2022 → Likud 2026.** Choose the sourced election-specific lists, then choose Copy votes or Replace list. Copy votes transplants the source snapshot's exact count under an explicit destination budget policy; it leaves target identity/roster alone. Replace list previews identity, votes, roster and constituent data, plus agreement/grouping/coalition dependencies. Keeping 2026 rules while importing a 2022 roster is a labelled counterfactual, not a restored official result. Do not infer the 2026 data from the owner's example; load whatever verified dataset/status is actually available.

## Hard cases that should drive the design review

| Case | Required behavior or decision |
|---|---|
| Joint list later divides into separate contestants | Aggregate comparison is possible; allocating the old joint vote to components needs explicit hypothetical weights. Candidate/seat composition is not a measured vote split. Preserve an unsplit option. |
| Several lists merge, with one constituent appearing elsewhere | Check for duplicate counting across all selected mappings. A source row cannot be implicitly consumed twice by one bulk operation. User-defined duplication is a separate explicit experiment. |
| Same name/letters, different organization or era | Scope identities to election and registry; offer reviewed matching. Leader migration is not succession. |
| Source is already synthetic or manually mapped | Retain that origin and mapping status; copying does not convert it into historical evidence. |
| Different electorate or valid-total budget | Raw count and share can answer different questions. Show target totals before/after; do not silently scale unrelated lists or change registered voters. |
| Share copy and integer rounding | Define whether the target valid total is fixed. With other votes fixed, a target share p requires solving x/(others+x)=p; 100% can be impossible unless others become zero. Handle zero denominators and distribute remainders deterministically. |
| Source or target withdrew | Held votes and invalid-ballot bookkeeping must stay consistent. Ask to reinstate when required; never copy votes into a withdrawn list and later duplicate them on reinstatement. |
| Different thresholds/methods/candidate-cap eras | Retain each side's rules by default. Copying rules is an explicit experimental operation; show effects of both inputs and rules. Do not claim seat differences are caused solely by votes. |
| Agreement partner does not exist, already has a partner, or is replaced | Map or explicitly omit the affected agreement with a visible explanation; historical constraints still apply. No dangling IDs or silent pruning. |
| Roster missing/truncated, duplicate people, historical name change | Preserve coverage flags, candidate identity/order and known uncertainty. Recalculate elected members only to supported roster depth. Never invent missing candidates. |
| Different bloc/family definitions | Show “different groupings”; compare lists or adopt one explicitly mapped analytical scheme. “No bloc”, unknown and zero seats are separate states. |
| A source draft changes after preview | Preview captures a source snapshot and target revision. Reject/review a stale target rather than apply to unexpected state; later source edits do not affect a completed snapshot copy. |
| Both sides opened from one saved scenario | Independent draft state and histories; saving one must not silently overwrite the other's changes. Save-as and deliberate overwrite remain distinct. |
| Swap during selection, mapping or preview | Cancel or explicitly retarget pending operations using stable scenario identities, never just visual position. Delta signs reverse; histories remain with their drafts. |
| Undo after copy and subsequent independent edit | Single-destination transaction undo restores the exact pre-copy state. Define global versus focused-side undo visibly; do not undo an unrelated side accidentally. Cross-side operations need coordinated history if introduced. |
| Batch has one invalid item | Entire operation stays unapplied; identify which row needs attention. Preview counts must distinguish selected, compatible and unmatched rows. |
| Cross-era roster/party import into a target | Translate IDs and dependencies; retain source election metadata as provenance. Candidate origin IDs from another election cannot masquerade as target official origins. |
| National edit versus map/locality comparison | National copies do not fabricate locality or ballot-station allocations. Keep official local results labelled unchanged or mark the requested derived local view unavailable. |
| Missing baseline, unpublished result, loading failure | Preserve both drafts and selection; show source status and recoverable failure. Never silently fall back to a different comparator under the same label. |
| Small viewport or edited row becomes equal | Keep the row and focused control in place until interaction finishes. Offer an explicit refresh of the Difference filter; no disappearing targets. |
