# Improving the app’s Hebrew

Research and editorial pilot · 7 November 2026 · source baseline `d0bd5b26880114ddebb06f3000224ade2c0358a2`.

**Recommendation:** use a project-specific Hebrew editing brief and sourced terminology, a native Hebrew editor for the initial pass, and local spelling/terminology checks for regression prevention. A small existing Hebrew skill can help the editing pass; installing a connector alone will not fix the writing. Microsoft Editor is a credible optional second opinion. Do not buy LanguageTool, Grammarly or Ginger for Hebrew proofreading.

This is research, not an app patch or an installed skill. The 25 edits below are proposals generated in this session with `gpt-6.1-sol` (high reasoning), using the source contexts and editorial constraints recorded here, then manually checked against those contexts; they have **not** been approved by a native editor, tested in the UI, or compared experimentally with another model/tool. No paid API, installation of a language tool, or disclosure of user scenarios was used.

## Decision and method

Question: which practical combination improves short, accurate Israeli Hebrew UI copy without changing electoral meaning? Assess coverage of spelling, grammar, idiom/register and electoral semantics separately; also consider automation, price/licence, and where text goes. A claim of Hebrew support is not a measurement of editing quality.

Read PRODUCT.md, DESIGN.md, the current CHANGELOG, the common/task briefs, relevant owner messages (including the request for concise caveats and rejection of literal political labels), and the existing glossary research. Searched workstreams: Hebrew linguistic tools; mainstream proofreaders; official language/terminology references; skills/MCP/models; professional editors. The challenge pass looked specifically for Hebrew exceptions in Microsoft support, newly multilingual Grammarly, actual Hebrew editing skills, and limits of spelling-only checks. Availability findings below come from vendor/project pages, not reviews or star counts.

Provenance labels: **Observed** = repo text; **Documented** = inspected first-party material; **Judgment** = editorial recommendation; **Estimate** = planning allowance; **Unverified** = not demonstrated here. Prices are observations, not quotes or guaranteed current offers. No market-wide or exhaustive coverage is claimed.

## Diagnosis and 25-string pilot

The dominant issue in this purposive sample is **wording rather than misspelling**: English-shaped metaphors, compressed technical nouns, bureaucratic passives, and labels that omit what is being counted. Some existing strings are serviceable; this is a sample for editing, not a defect-rate estimate.

Classification: T = translationese/calque; W = word order or unclear attachment; R = register; G = gender/number agreement; K = spelling consistency; P = punctuation; E = electoral terminology. These are editorial assessments, not automatic Academy violations. In particular, ניתן and passive constructions are not inherently wrong. No general מלא/חסר inconsistency was established in these 25; row 24 is a proper-name spelling inconsistency, not evidence for blindly applying כתיב מלא to names.

## Skills, MCP and a different model

**Existing, relevant skill:** [skills-il/localization’s hebrew-ai-text-humanizer](https://github.com/skills-il/localization/tree/master/hebrew-ai-text-humanizer) (S12). Inspected its SKILL.md and pattern catalogue: MIT; targets awkward translated Hebrew, register, addressing, agreement and punctuation; optional local Python scanner, with a manual route. These are author-defined heuristics, not a validated Hebrew grammar engine. The distinction between style advice and actual rules is useful. Its blanket preferences need contextual judgment: an accurate technical term or a valid passive is not a defect. It does not supply our electoral glossary. Text goes wherever the chosen model processes it; the skill itself is not a privacy guarantee. **Worth a pinned, reviewed trial, not a global install or automatic rewrite.**

**Existing broader plugin:** [yodem/hebrew-book-producer](https://github.com/yodem/hebrew-book-producer) (S13), MIT, documents separate linguistic-editing and proofreading agents. Its manuscript-production workflow and optional CandleKeep/Sefaria dependencies fit books rather than UI copy. A repository’s existence proves neither editing quality nor portable integration. Model usage costs remain. Do not install an entire production system to edit labels.

**MCP:** targeted public searches for Hebrew proofreading MCP servers did not identify a purpose-built, first-party, evaluated service worth recommending. This is a bounded “not found”, not proof none exists. A wrapper around a model or LanguageTool does not improve Hebrew coverage. No new connector is necessary for this pipeline.

**Different-model pass:** run the same context-rich packet through an independently chosen general model already available to the owner, and optionally [DictaLM-3.0-1.7B-Instruct](https://huggingface.co/dicta-il/DictaLM-3.0-1.7B-Instruct) (S14), whose card documents Hebrew/English training, Apache-2.0 and local inference examples. Do not infer superior UI editing from a Hebrew benchmark or small-model availability. Self-hosting removes per-request provider fees but adds compute/setup; local inference can keep strings local. Hosted models have provider-specific retention and token costs, not verified here. No model winner is established, and no paid API experiment was run.

For a fair next experiment, use the 25 items with surrounding UI purpose, placeholders and fact constraints. Compare: original, this pilot, chosen second model, Microsoft Editor where supported, and native editor. Hide author identity; ask the owner/editor to judge naturalness, brevity, and meaning preservation separately. A changed negation, source qualifier, count or uncertainty level fails regardless of fluency. Keep a small withheld set before reusing accepted examples in prompts. Record model/version/date/prompt and actual usage; do not advertise a “Hebrew quality score” from regex hits. This proposed evaluation is not measured evidence yet.

## Professional review and realistic budget

Ask for an **עורך/ת לשון עם ניסיון במיקרוקופי ובמונחי בחירות**, not simply an English→Hebrew translator. A native speaker may spot awkwardness without knowing electoral distinctions; a specialist editor may still need a subject reviewer. Use a paid contextual sample of these 25 strings before commissioning the whole inventory.

First-party price anchors (S15):

- [Shirley Guy](https://www.shirleyguy.co.il/linguistic-editing/) publishes an indicative market range for comprehensive editing including rewriting of ₪50–80 per 250 words: **₪200–320 per 1,000 words**, arithmetic conversion of the author’s estimate, not a seller quote or independently measured market rate.
- [Kamatz Katan](https://www.kkatan.com/cost) lists ₪50 proofreading, ₪100 language editing and ₪150 content editing per 250-word page: **₪200 / ₪400 / ₪600 per 1,000 words**, with a **₪400 minimum** and VAT excluded. The same page says websites may need a global/hour-based quote.
- Therefore budget **₪200–600 per 1,000 words as a planning range**, plus any minimum, tax and platform fee; contextual UI review can exceed it. Do not extrapolate an entire-app price without counting unique strings and agreeing how to charge placeholders, repeated labels, screenshots, glossary work and revision rounds. An older academic price list is not a good UI quote.

Sourcing options: direct editor above; [Fiverr Hebrew editing listing](https://www.fiverr.com/may2311/proofread-and-edit-your-hebrew-text); [ProZ Hebrew jobs/directory route](https://www.proz.com/hebrew-translation-jobs/); [XPlace Hebrew editor discovery](https://www.xplace.com/il/u/ofer2771) (S16). ProZ/Fiverr pages were opened; XPlace’s extracted profile was mostly an unrendered template, so its expertise is not independently assessed. These are places to obtain samples/quotes, not endorsements of individuals. No one was contacted or commissioned.

Human review is naturally a manual approval step; accept returned edits by stable string ID or reviewed diff, not by scraping a platform. Agree deliverable/usage rights, confidentiality, whether the editor uses external AI, and retention/deletion. Send public UI copy and context only; there is no reason to send private scenarios, browser storage, API credentials or unpublished owner comments.
